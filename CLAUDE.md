# CLAUDE.md

This app consumes the shared `lyra-ui` design system via a live source alias (`@nicecxone/lyra-ui`), not a local component library. Before writing or editing any UI code here:

- Import UI atoms from `@nicecxone/lyra-ui` — never build or reach for a local `src/components/ui/*` reimplementation of something that already exists there.
- Check `lyra-ui/src/index.ts` and that component's `__stories__` file *before* building anything — reuse the existing component, and match the exact markup shape shown in its story, not just the prop types (e.g. a plain labeled `Checkbox` is a manual `<label>` wrapper around it in most stories, not the `label` prop).
- When building a form or any form-like set of fields, consult `Input.stories.tsx`'s and `Select.stories.tsx`'s own "Default" playground controls first (Label only, With buttons, Buttons position, Button type, Icon buttons, Button size, Button count, Horizontal, Help, Error, Max width) and compare them against the prototype/design being requested — then compose the field from that matching combination of props, instead of hand-rolling markup for a variant one of these controls already demonstrates.
- Never modify a `lyra-ui` core component from here. If something this app needs doesn't exist yet in `lyra-ui`, that's a signal to add it there — not approximate it locally.
- When a screenshot or prompt describes a component ambiguously, or nothing in `lyra-ui` visually matches what's shown, ask the user which component to use or whether to build something new — don't guess. If building something new, keep it local to this app; don't add it to `lyra-ui` until the user explicitly asks (see `PROJECT_SUMMARY.md`'s "When a screenshot/prompt doesn't clearly match an existing component").
- **A screenshot of an older/differently-styled interface (a different corner radius, size, or color than any current lyra-ui component) is still asking for the matching real component — not a from-scratch reproduction of its exact shape.** Reach for that component's props/className first — but only for properties it actually supports varying — before treating a shape mismatch as proof a whole new component is needed (see `PROJECT_SUMMARY.md`'s "A screenshot of an older/differently-styled interface still means 'use the matching real component'" — the `OnlineHelpButton` incident).
- **Picking the right component doesn't automatically mean the right size was picked for it.** After reusing an existing component, separately check its actual neighbors' real rendered size (`h-*`/`w-*` class, not a guess at which named size "sounds" biggest/most important) and match that specific one — don't pick a size for how the button feels it should read. See `PROJECT_SUMMARY.md`'s "Picking a real size token isn't enough" entry (the same `OnlineHelpButton` build: a fabricated `h-12 w-12`, then a real-but-wrong `icon-2xl`, before landing on `icon-lg` — the size its actual rail siblings use).
- **A className override isn't valid just because a screenshot shows it — check whether the component actually supports varying that property at all.** The same `OnlineHelpButton` build also picked up a `rounded-full` override to match a screenshot's rounder corners, but `Button`'s `buttonVariants` (button.tsx) hardcodes `rounded-lyra-sm` identically across every variant/size — no circular option exists to opt into, so this was a fabricated value, not a real override (same failure as the size guesses, just applied to shape). See `PROJECT_SUMMARY.md`'s "A component's real shape isn't a free-form override either" entry.
- **Every `TabList` gets `overflowMenu` — always.** There is no case in this app where a fixed row of tabs should be allowed to just clip or wrap once it runs out of room; every `TabList` usage turns on `overflowMenu` (tabs.tsx) so it collapses to "active tab + N More" instead. Pick `overflowBreakpoint="compact"` (content-aware measurement) instead of the default `"wide"` (fixed ≤991px) specifically for a `TabList` living in a narrow/resizable host — a docked panel, an interior panel — where a fixed pixel threshold would be permanently wrong in one direction or the other; `"wide"` is fine for a page-level tab bar. See `PROJECT_SUMMARY.md`'s "Every TabList needs overflowMenu" entry (the Monitor dashboard's workspace tabs, built without it the first time).
- **A `TabList`+`overflowMenu` layout class (width, flex sizing) goes on a wrapping `<div>` you own, never on `TabList`'s own `className`.** `overflowMenu` renders the full tab row and the collapsed "active + N more" row as two separate siblings inside `TabList`'s own internal wrap div — a `className` passed straight to `TabList` only ever reaches the full row, never the collapsed one. See `PROJECT_SUMMARY.md`'s "TabList + overflowMenu" entry, and `lyra-form-generator`'s `FormDetailPage.tsx` for the reference pattern this was modeled on.
- **A page/panel's tab strip is always fixed to the top of its scrolling container — it never scrolls away with the content below it.** Give the tab row `shrink-0` and keep it *outside* whatever wrapper has `overflow-y-auto`, so the tabs stay put and only the page header/body content scrolls underneath. This is a standing layout rule for every tab bar in this app, not a one-off — see the Monitor dashboard (`MonitorDashboardPage.tsx`) for the reference structure.
- **`overflowBreakpoint="wide"` already scrolls with chevrons above its own ≤991px collapse threshold — don't build a second scroll mechanism locally.** If a `"wide"`-mode `TabList`'s tabs don't fit but the row hasn't dropped to ≤991px yet, left/right chevron buttons appear automatically (tabs.tsx) to scroll one tab at a time. This is built into `TabList` itself — nothing to add on this app's side beyond turning on `overflowMenu`.
- **Card/grid layout responsiveness is always container-query-based, never a Tailwind `sm:`/`md:`/`lg:`/`xl:` viewport prefix.** Those only react to the browser window resizing, not to the left nav opening/closing or a docked panel taking space. Check `lyra-ui` for an existing container-query class first (`.lyra-container-grid`, `.lyra-form-grid`, `.lyra-metric-row`, `.lyra-card-split`) — since this app can't modify `lyra-ui` components directly, ask for a new dedicated one to be added there if none fits, rather than reaching for a viewport prefix locally. See `PROJECT_SUMMARY.md`'s "Card/grid responsiveness must be container-based" entry (the Monitor dashboard's card grid and summary-card split, both built with viewport prefixes the first time) and the Monitor dashboard (`MonitorDashboardPage.tsx`) for the reference usage.
- **`Tab` already truncates its label and shows a "full label" tooltip on hover once it's actually truncated — nothing to add here.** Built into `Tab` itself (lyra-ui); every tab in this app gets it automatically.
- **Every page in this app is `AdminShell` (lyra-ui) — never a hand-rolled root layout with its own `SidePanel`/`PageHeader`/pin-state.** The Monitor dashboard went through three wrong versions before landing here: a hand-rolled fixed `<div>` side menu, then a real `SidePanel` wrapped by a page-owned root `<div>` (with its own manually re-implemented pin/hover/container-width-guard state, duplicating what `AdminShell` already provides), before finally being rebuilt on `AdminShell` itself per an explicit "all new pages should be in the AdminShell — why would you hand roll your own root layout??" correction. If `AdminShell` doesn't yet support something a new page needs (a view-switcher badge, exact tree selection, a page header subtitle, etc.), that's a signal to extend `AdminShellProps` in lyra-ui — see `navHeaderBadge`/`navExactSelection`/`navKey`/`pageSubtitle`, all added for exactly this — not a reason to bypass it. See `MonitorDashboardPage.tsx` for the reference `AdminShell` usage (mirrors `OutboundCampaignsPage`'s own), and `../lyra-ui/PROJECT_SUMMARY.md`'s "AdminShell gains navHeaderBadge/navExactSelection/navKey/pageSubtitle" entry.
- **A tree nav's per-leaf icon uses `TreeMenuChild.icon` (lyra-ui) — don't hand-roll icon markup alongside `TreeMenu`.** Every leaf in `CallCentersSideMenu.tsx`'s node data carries the same fixed-color icon this way, matching the reference screenshot.
- **Pages are real URL routes (`react-router-dom`), not local `useState` page-switches.** `main.tsx` wraps `<App />` in `<BrowserRouter>`; `App.tsx` renders `<Routes>` with `/monitor` (home — an unmatched path, including bare `/`, redirects there via a trailing `<Route path="*" element={<Navigate to="/monitor" replace />} />`) and `/configure`. `Sidebar.tsx`'s `activePage`/`onNavigate` props are unchanged in shape, but `App.tsx` now derives `activePage` from `useLocation()` and calls `useNavigate()` instead of a local `SidebarPage` state variable — any new page needs its own `<Route>` here, not a new state value to switch on.
- **Monitor's card region (metric grid + summary card) renders `DashboardTemplate maxWidth="none"` (lyra-ui) — not a bare wrapper `<div>`.** Mirrors lyra-ui's `Templates/Dashboards` → "Full Width" story (same shell, `maxWidth="none"` for a full-bleed dashboard instead of the default `1200`-capped column), but with Monitor's own real cards/data, not that story's placeholder ones. The "Showing data for: {label}" row (plus Duplicate/Edit/Fullscreen icon buttons) is this page's toolbar (first child inside `DashboardTemplate`) — deliberately not the generic Quick Search/filter-chip/action-icon `TableToolbar` that story's demo uses; that toolbar's contents are all invented demo content, and Monitor already had real toolbar content of its own. The old filled "Settings" text button was later replaced with an icon-only Edit (`Pencil`, `variant="icon" size="icon"`) button, and a `Maximize2`/`Minimize2` fullscreen toggle was added after a divider — both pulled from the same template toolbar's icon-button styling. Unlike the story's decorative/padding-only fullscreen, Monitor's toggle hides the workspace tab strip for more vertical room; the toolbar row (and its own now-"Exit Fullscreen" button) stays visible. See `MonitorDashboardPage.tsx`'s own doc comment and `../lyra-ui/PROJECT_SUMMARY.md`'s dashboard-template entries.
- **A chart's height inside a `.lyra-card-split` region uses the shared `.lyra-card-split-chart` class (lyra-ui), never a one-off `h-[…px]`.** It's breakpoint-aware (420px in the row state, 260px once `.lyra-card-split` stacks at its own `@container (max-width: 480px)`) — a hardcoded fixed height doesn't shrink when the card stacks, and the stat boxes' height plus that same flat number can blow past `DashboardCard`'s `max-h-[600px]` body cap, forcing the whole card to scroll. See `../lyra-ui/PROJECT_SUMMARY.md`'s "`.lyra-card-split-chart`" entry (the incident: Monitor's own "Outbound Email" chart, hardcoded to `h-[420px]` unconditionally).
- **Monitor's "Outbound Email" summary card renders a real `BarChart` (lyra-ui), not `EmptyState`.** Vertical orientation (`BarChart`'s own default — upright columns, day categories on the x-axis, numeric email amount on the y-axis; started as `orientation="horizontal"` per the original ask, later switched to vertical per "make the bar chart in outbound campaigns a vertical chart"), two grouped series (Emails Launched/Emails Remaining) — `EMAIL_CHART_DAYS`/`EMAIL_CHART_SERIES` in `MonitorDashboardPage.tsx` are static/dummy like everything else on this page, just non-zero so the chart has something to draw. `BarChart` is the first axis-labeled chart component in lyra-ui (`DonutChart`/`Sparkline` are both bare, no axes/legend) — added specifically for this card; see `../lyra-ui/PROJECT_SUMMARY.md`'s "BarChart — the first axis-labeled chart-type component" entry.
- **Monitor's date filter is ONE toolbar-level `DateRangeFilterChip` (lyra-ui), not a per-card control.** Originally each card had its own `headerActions={<DateRangeFilterChip />}` (a single-select "Date: {label}" `RadioGroup` popover, the same control `AgentDashboard`'s own cards use) — seven independent, uncoordinated filters. Per "remove the individual filters in the dashboard cards ... and add a filter to the toolbar," consolidated into one `DateRangeFilterChip` in the toolbar row, controlled by `dateFilter` state (`useState<MonitorDateRange>("today")`) in `MonitorDashboardPage.tsx` itself. Options are Today/Yesterday/Last 7 days/Last 30 Days/Last 90 Days (`MONITOR_DATE_FILTER_OPTIONS`, no "Custom") — `DateRangeFilterValue` gained `"last30"`/`"last90"` in lyra-ui specifically for this (additive; every other consumer's default option list is untouched). `dateFilter` lives independent of `selectedId`/`view` (the tree-selection state), so it persists across call-center clicks with no dedicated persistence code — that's just what "state nothing else resets" means. Every metric card and the "Outbound Email" chart/stat boxes read from `METRIC_CARDS_BY_RANGE[dateFilter]`/`EMAIL_CHART_BY_RANGE[dateFilter]`, not one fixed dataset — see `../lyra-ui/PROJECT_SUMMARY.md`'s "Monitor's per-card date filters consolidated into one toolbar-level filter" entry, and `../lyra-ui/CLAUDE.md`'s `Exclude<DateRangeFilterValue, ...>` rule for why widening a shared type like this needs care.
- **Every `DashboardCard` on the Monitor page opens a right `InteriorPanel` (lyra-ui) on click or via its own kebab "Edit" item — both converge on the same `openInteriorPanel(title)` helper in `MonitorDashboardPage.tsx`.** A clickable card needs a consumer-supplied `kebabMenuItems` array with a real `onClick` on "Edit" (the default kebab items are decorative), and the panel itself must sit as a flex sibling of the scrolling content column, in a row placed *after* the workspace tab strip — that's what "opens beneath the tabs" means structurally. The toolbar's own Edit icon button (Duplicate/Edit/Fullscreen row) calls the SAME helper with `"Edit Dashboard"` for a dashboard-wide edit, not a fourth separate panel — one `InteriorPanel`/one open+title state, three trigger points. See `MonitorDashboardPage.tsx`'s own doc comment and `../lyra-ui/PROJECT_SUMMARY.md`'s "Outbound-Campaigns' Monitor cards click (or kebab 'Edit') to open a right InteriorPanel" entry.
- **"Online Help" and "Ask AI" share ONE docked slot and ONE float slot between them — never two docked, never two floating at once.** Coordinated in `App.tsx` via `openPanel(key)`/`dockPanelExclusively(key)` (a small `PanelKey`/`PanelHandle` abstraction over both panels' existing independent state groups, NOT a lyra-ui change — lyra-ui's `Draggable`/`AiPanel`/`DraggablePanel` are all untouched). Rules: (1) opening a panel while the other is open+docked replaces it outright (the old one closes, the new one takes the docked slot); (2) opening a panel while the other is open+floating leaves the floating one alone and docks the new one beside it; (3) explicitly re-docking a floating panel while both are open swaps whichever one WAS docked back to floating, instead of closing it — this last rule is lyra-ui's own documented "single-dock rule" (see `draggable.tsx`'s "Multi-Panel Z-Index & Docking Rules" comment) and the same `dockPanelExclusively` pattern agent-next-gen-v1's `AgentNextGenPage.tsx` already uses for its own (larger, un-coordinated-on-open) panel set — reused/generalized here, not reinvented. Both panels' own trigger buttons (`Sidebar`'s Help icon, Monitor's "Ask AI") call `openPanel("help"|"ai")` instead of a bare toggle; both panels' `onVariantChange` handlers call `dockPanelExclusively` when becoming `"docked"`. Any THIRD Draggable-backed panel added to this app in the future should extend `PanelKey`/`getPanelHandle` rather than growing a separate, uncoordinated state machine.
- **Clicking a floating panel brings it to front — `topPanel` state + `onInteract` on each panel, z-index 10000 for the top one / 9999 for the other.** This is lyra-ui's own documented consumer contract (`draggable.tsx`'s "Multi-Panel Z-Index & Docking Rules"), the same `topPanel` pattern agent-next-gen-v1's `AgentNextGenPage.tsx` already uses. Only visibly matters once both panels are floating at once (reachable via manually undocking one while the other is already floating — the dock/float coordination above doesn't prevent that) — before this fix both floats hardcoded the same z-index, so whichever rendered later in JSX always won regardless of click order. **The "bring to front" handler must be `DraggablePanel`/`AiPanel`'s own `onInteract` prop (which lyra-ui forwards onto `Draggable`'s actual root node — the element that moves via CSS `transform` during a drag), never an `onMouseDown` on an app-level wrapper `<div>` that's an ANCESTOR of the panel.** An ancestor's layout box does not move with a descendant's `transform` — it was originally wired as `onMouseDown` on a `pointerEvents: "auto"` div wrapping `{helpPanel}`/`{aiPanel}` inside the `pointerEvents: "none"` float positioning div, and after dragging a panel away from its start position, that now-invisible ancestor div was left behind, still `pointer-events: auto`, sitting exactly where the panel USED to be — which happened to be right under the page header's own Secondary/Primary/Ask AI buttons, silently swallowing clicks meant for them (repro: open Ask AI → undock → drag left → header buttons stop responding). `draggable.tsx`'s own `onInteract` prop doc comment warns about this "ghost hit area" explicitly; `Draggable`'s root already sets `pointer-events: auto` on itself, so the wrapper div needs no pointer-events override at all — it now exists purely to hold the fade/slide open-close animation styles. Fixed by removing the wrapper's `onMouseDown`/inner `pointerEvents:"auto"` div and passing `onInteract={() => setTopPanel(...)}` directly to `<DraggablePanel>`/`<AiPanel>` instead.
- **Monitor's page header has real "Secondary"/"Primary"/"Ask AI" `pageActions` (`AdminShell`) — the same composition lyra-ui's own `AdminShell.stories.tsx` "With Page Header" story demonstrates.** "Ask AI" is wired to a real `AiPanel`, but the panel and its docked/float/resize state live in `App.tsx` — ONE shared instance for the whole app (mirrors the existing "Online Help" `DraggablePanel` state machine already there), threaded into `MonitorDashboardPage` via an `onAskAiToggle` prop rather than owned by the page itself. Any future page that wants its own "Ask AI" trigger should reuse this same app-level panel/state (thread the same callback down), not build a second one. See `MonitorDashboardPage.tsx`'s own doc comment and `App.tsx`'s "Ask AI panel" section.
- **The card whose panel is currently open renders `variant="info-strong"` instead of `"neutral-subtle"` — the same selected-card treatment `DashboardQueue` (lyra-ui) already uses, not a new mechanism.** Each card's `variant` in `MonitorDashboardPage.tsx` is conditional on `interiorPanelOpen && interiorPanelTitle === {that card's title}`; the toolbar's `"Edit Dashboard"` trigger deliberately never matches a card's title, so it never falsely selects one. See `../lyra-ui/PROJECT_SUMMARY.md`'s "the triggering card shows a selected state while its panel is open" entry.
- **Never use primary/brand or a raw light/dark color for a dashboard icon or chart series in this app — icons get a subtle `Icon` `background` (never `"primary"`), chart series get an accent (data-viz) `colorVar` from `--lyra-color-accent-{slate,red,orange,yellow,lime,green,teal,purple,pink}-strong` (never `accent-blue-strong`, and never a `status-*`/`fg-*` token used as a generic color).** Exception: a chart whose colors map onto a real semantic element (status/success/warning/critical) may use that element's own color — the rule targets arbitrary categorical series with no inherent meaning, like Monitor's own "Emails Launched"/"Emails Remaining" `BarChart`, which is exactly the incident that prompted this rule (it originally shipped with `status-info-strong`/`fg-secondary`, fixed to accent colors). See `../lyra-ui/CLAUDE.md`'s and `PROJECT_SUMMARY.md`'s matching entries.
- Every modal's outer card uses `Container variant="modal"`, never a hand-rolled div.
- Use the shared `assets/app-icon.svg` mark for the app logo/smiley — never `CXoneSmiley` or a one-off hand-rolled SVG.
- Before reaching for a raw Tailwind utility value (spacing, sizing, radius, etc.), check other lyra-ui components/stories first for the established token.

Full rationale, worked examples, and the "why" behind each of these live in `../lyra-ui/PROJECT_SUMMARY.md` (see Important Patterns, Scope Rules, and the Post-layout QA checklist) — read that file before making non-trivial UI changes here.

## Sync check (do this first, every session)

This app depends on a live sibling checkout of `lyra-ui` (see the `@nicecxone/lyra-ui` alias path in `vite.config.ts` — currently `../lyra-ui`), not a versioned package. `.lyra-ui-sync` in this repo's root records the `lyra-ui` commit hash this app was last checked against.

1. Confirm the sibling path from `vite.config.ts`'s alias and check it's a real git repo (`git -C ../lyra-ui rev-parse HEAD`). If it's missing entirely (this project was moved without lyra-ui alongside it, or lyra-ui hasn't been cloned yet), skip this check silently — don't block on it.
2. Otherwise, diff since last sync: `git -C ../lyra-ui log --oneline "$(cat .lyra-ui-sync)"..HEAD`. Nothing printed means nothing changed — move on.
3. If there are new commits, read `../lyra-ui/PROJECT_SUMMARY.md` for a human-readable description of what those changes actually are (its "Key Components" entries and changelog-style bullets exist for exactly this). Summarize for the user what's new and whether anything in this app looks like it should be migrated to use it (same categories as the rules above — a hand-rolled pattern that a new/changed component now replaces).
4. Ask before migrating anything — don't silently rewrite pages.
5. Whether or not the user chooses to migrate, once they've seen and responded to the new changes, update `.lyra-ui-sync` to `lyra-ui`'s current HEAD hash (`git -C ../lyra-ui rev-parse HEAD`) so the same commits aren't re-flagged next session.

This same file/procedure is what a freshly duplicated copy of this template repo should keep doing — duplicating this repo carries `.lyra-ui-sync` and this `CLAUDE.md` along with it, so a new project built from this template inherits the sync check automatically as long as it keeps `lyra-ui` as a sibling checkout (or its `vite.config.ts` alias is updated to point at wherever `lyra-ui` actually lives).
